# Engineering standards

Read before writing code. Code quality wins over deadlines in this project.

The goal: anyone can open any file and understand what it is for and roughly how it works, without having to understand the code around it.

## Clean code

- **One job per file and per function.** If a name needs "and" to be honest, split it.
- **Names carry the meaning.** File, function and variable names say what they are and why they exist. No header comments per file; if a file needs one, its name or its scope is wrong.
- **Comments explain why, never what.** Use them for non-obvious constraints, trade-offs and workarounds, not to narrate code.
- **Small functions, flat control flow.** Prefer early returns over nesting. Keep functions short enough to read without scrolling.
- **Explicit dependencies.** A function gets what it needs through its arguments or imports, not through hidden global state.
- **Business logic is pure and framework-free.** Grading, scoring and validation are plain TypeScript functions that know nothing about Convex, React or Next.js. Convex functions and React components are thin glue that call them.
- **No dead code, no speculative code.** Build what the current milestone needs; delete what is no longer used.
- **Types document intent.** Name domain types (`Question`, `TeamAnswer`) instead of repeating inline object shapes; avoid `any`.

## Tests

- **Colocated:** every code file `foo.ts` / `Foo.tsx` has a `foo.test.ts` / `Foo.test.tsx` next to it.
- **Coverage threshold: 80%** (lines, branches, functions, statements), enforced in the Vitest config so the test run fails below it.
- **Tests read as documentation:** `describe` the unit, and name each case after the behaviour it checks ("gives 3 points within ±1").
- **Tools:** Vitest; `convex-test` for Convex functions (in-memory database, edge-runtime environment); React Testing Library for components.
- Convex skips any file in `convex/` whose name has more than one dot, so `*.test.ts` files there are never deployed.
- Two Vitest projects: `convex/**` tests run in `edge-runtime` (Convex's runtime), `src/**` tests in `jsdom` (a simulated browser). Coverage counts every file under `src/` and `convex/`, including files with no tests yet.
- The pre-commit hook (husky) runs lint, typecheck and tests with coverage; a commit fails if any of them fails. Don't bypass it with `--no-verify`.

## Exceptions

Exceptions to the test rules are made on purpose and listed here with a reason. The same list is excluded from coverage in the Vitest config; keep the two in sync.

| Path | Reason |
|---|---|
| `convex/_generated/**` | Generated by `npx convex dev` |
| `src/components/ui/**` | shadcn/ui components, vendored library code |
| `*.config.*`, `next-env.d.ts` | Tool configuration |
| `src/app/**/layout.tsx` | Route shells that only wrap children (providers, the host gate), no logic |
| `src/app/ConvexClientProvider.tsx` | Wires the Convex client, no logic |
| `**/*.d.ts`, type-only files | No runtime code to test |
| `**/*.setup.ts` | Shared test setup, only runs inside tests |
| `src/app/**/page.tsx` | Thin routes: read params, render one feature component |
| `convex/schema.ts`, `convex/**/table.ts` | Declarations only; exercised by every Convex function test |
| `convex/questions/**/*Content.ts`, `convex/questions/acceptedItem.ts`, `convex/questions/numberOrNull.ts` | Question shape validators, declarations only; exercised by every question function test |

## File structure

Agreed in D11. Three layers, with dependencies pointing inward toward the domain:

| Layer | Folder | What it holds | May import |
|---|---|---|---|
| Domain | `src/domain/` | Pure quiz rules: grading, scoring, normalizing | Nothing at runtime; types only from `convex/` |
| Backend | `convex/` | Tables, validators, queries, mutations | `src/domain/` |
| Frontend | `src/features/`, `src/app/` | Screens and UI | `src/domain/`, `src/components/ui/`, the Convex `api` |

```
convex/
  schema.ts                      # combines the tables from each folder
  quizzes/  rounds/  questions/  # one folder per table:
    table.ts                     #   table definition + its validators
    queries.ts                   #   reads
    mutations.ts                 #   writes
  questions/types/<type>/        # one folder per question type: <type>Content.ts (later its answer validator)
  questions/questionContent.ts   # union of all content validators, and the QuestionContent / QuestionType types
  auth/                          # passphrase check and hostQuery / hostMutation wrappers (D21)
  media/                         # upload URLs, attaching media, media URLs
  shared/                        # small helpers used by several tables, such as getOrThrow

src/
  domain/
    questionTypes/<type>/        # rules for one type: <type>Rules.ts (max points, problems), later its grader
    questionTypes/registry.ts    # type → rules, typed as a complete map over QuestionType
    questions/                   # cross-type functions using the registry: findQuestionProblems, maxQuestionPoints, createEmptyContent
    rounds/  ordering/  text/  time/ # which types fit a round, list moves, number and answer-key text, "Sparat för …"
    screenSequence/              # derives the TV screen order from a quiz (D15)
    scoring/  matching/          # leaderboard, fuzzy text matching …
  features/
    host/                        # the two hosts
      shared/                    # host session, useHostQuery / useHostMutation, header, confirm button
      hostGate/                  # login screen and passphrase check
      authoring/
        quizList/                # /admin: list, create, copy, delete
        editor/quiz|rounds|question/  # /admin/quizzes/[quizId]: the three editor columns
        questionEditors/<type>/  # editor for one type, plus registry.ts (label + editor per type)
        questionEditors/fields/  # form fields shared by the type editors
        shared/                  # used by several authoring features: autosave, sortable lists, remove buttons, the keyboard drag test helper
        media/                   # uploads and previews
      liveControl/  scoreHistory/
    player/                      # teams on their phones
      join/
      answering/<type>/          # answer input for one type, plus registry.ts
    tv/                          # the shared screen
      screens/                   # lobby, rules, question, answer, leaderboard …
      questionDisplays/<type>/   # TV display for one type, plus registry.ts
    home/                        # the start page at /
    shared/                      # used by more than one audience: logo (brand/), map …
  components/ui/                 # shadcn/ui primitives
  app/                           # routes only
```

Every code file has its `*.test.ts(x)` next to it (left out of the tree above).

### Rules

1. **Dependencies point inward:** `app` → `features` → `domain`, and `convex` → `domain`. `domain` imports only types from `convex/`, never runtime code.
2. **Route files are thin.** A `page.tsx` reads its params and renders one feature component; no logic.
3. **Convex functions are thin.** Check the host, load data, call domain logic, write. Rules live in `src/domain`.
4. **No imports across audiences.** ESLint blocks `host`, `player` and `tv` from importing each other; code they share goes in `features/shared/`, `src/domain/` or `src/components/ui/`. Within an audience, code several features use goes in `<audience>/shared/` (such as `host/shared/`); features otherwise keep to themselves, which review checks rather than lint (D23).
5. **Naming:** components `PascalCase.tsx`, everything else `camelCase.ts`. A file is named after its one main export. Functions start with a verb (`gradeNumeric`, `requireHost`).
6. **No barrel files.** No `index.ts` that only re-exports; import from the real file.
7. **Flat feature folders** until one holds about 8 files; add sub-folders when needed, not up front.
8. **Rules 1 and 4 are enforced by ESLint** import restrictions in `eslint.config.mjs`, not only by this document.
9. **Audience names, not device names** (`host`, `player`, `tv`): the split is who uses it and for what, not screen size.
10. **Aliases for anything outside the current folder:** `@/…` for `src/`, `@convex/…` for `convex/`. Features and domain code don't use `../` imports (enforced by ESLint), so the boundary rules can see where an import points. `convex/tsconfig.json` declares the same aliases, so Convex can typecheck and bundle domain code it imports. Inside `convex/` itself, files import each other relatively (`../auth/hostFunctions`), as Convex's generated code does; anything from `src/` is imported with `@/`. The frontend reaches Convex through `@convex/_generated/api`, and may import only types from other Convex files.
11. **Question types extend through registries (D14).** A type's parts live in a `<type>/` folder in each layer. Each layer has one `registry.ts` mapping every type to its part, typed `Record<QuestionType, …>`, so a new type does not compile until every part exists. Shared code never switches on the question type; it asks the registry.

### Where does it go?

- A rule about how many points an answer gets → that type's folder in `src/domain/questionTypes/<type>/`, next to its rules.
- A new field on questions → `convex/questions/table.ts` (or `convex/questions/types/<type>/<type>Content.ts` for type-specific content).
- A form the hosts use to write questions → `src/features/host/authoring/`.
- Something both the TV and the phones display → `src/features/shared/`.
- A new URL → `src/app/…/page.tsx` that renders a feature component.
- A host-only Convex function → `hostQuery` / `hostMutation` from `convex/auth/hostFunctions.ts`, never plain `query` / `mutation`.
- A host action triggered by a click (create, move, delete …) → wrap it in `useRunAction()` so a failure is shown to the host. Autosaves show their own failure next to the field.
- A field that can be "not filled in yet" → `null` in the validator (for example `correctIndex`), never a fake default that hides the editor's warning. Every number the hosts type uses `numberOrNull`; an empty field is `null`, never `NaN` (D28).
- A new question type → a `<type>/` folder and a registry entry in each layer: validators in `convex/questions/types/`, grader in `src/domain/questionTypes/`, editor, answer input, TV display. The compiler lists what is missing.
